# Brief: Italian, alongside English

- **Status:** approved
- **Date:** 2026-08-10
- **Branch:** `feature/i18n` (git flow, off `develop`)
- **Owner agent(s):** frontend (the site), backend (one seam), legal (the notice)

## Problem / goal

The site is written by someone in Taranto, invoices with an Italian VAT number,
and publishes a privacy notice governed by the Garante — in English only. An
Italian visitor reads a second language to learn who he is, and an Italian data
subject reads a second language to learn what is done with their data. The
second of those is the one that actually matters: GDPR art. 12 asks for a
notice in clear and plain language, and "plain" is not a property of the prose
alone, it is a property of the prose *and its reader*.

The goal is a complete Italian site — every word, both pages — reachable by a
crawler as a first-class page rather than as a variant of the English one, and
switchable by hand from anywhere on the site.

## Scope

**In scope**

- Italian at `/it/` and `/it/privacy/`; English stays exactly where it is.
- Every served string: markup, canvas labels, JS status messages, `alt` text,
  `aria-label`s, `<title>`, meta description.
- The contact form's server-side validation messages — the one place the
  language crosses into `services/api`.
- `hreflang` (both directions plus `x-default`), per-locale canonicals,
  `og:locale` / `og:locale:alternate`, `inLanguage` in the JSON-LD, and
  alternates in the sitemap.
- A language switcher in the footer (every page) and in the mobile drawer.
- A `revisions` entry on both privacy pages recording that the notice is now
  published in Italian.

**Out of scope**

- `/admin`. It is `noindex`, disallowed in robots.txt, and has exactly one
  user, who is the person who would be translating it. It stays English and
  gets **no** `hreflang` — an alternate pointing at a page that does not exist
  is a worse signal than none.
- Automatic redirection by `Accept-Language`. Deliberate, see below.
- A third language. The structure below takes one, but nothing here is built
  speculatively for it.
- Translating the notification email the API sends to the owner. It is read by
  one Italian speaker who does not need it translated — though it will now
  carry the locale the message was sent from, so he knows which language to
  reply in.

## Which service(s)

- [x] `services/site`
- [x] `services/api` — validation messages only
- [x] Contract change — an optional `locale` field on `POST /api/contact`

## The seam / contract

`lib/contact.ts` prints the server's 422 messages verbatim into the field
slots. Those messages live in `services/api/src/Validator.php` and are English
sentences ("Please enter your name"). An Italian form that reports its errors
in English is worse than no translation at all, because the failure is the one
moment the reader is already frustrated.

`POST /api/contact` gains one optional field:

```
locale: "en" | "it"    — absent or unrecognised ⇒ "en"
```

The response shape does **not** change: still `422 { message, errors: { field: [msg] } }`,
still the shape `fieldErrors()` expects. `Validator` picks a message table by
locale; that is the whole change. Codes were the alternative — the client
holding the strings, the server naming them — and were rejected: it breaks the
error contract this repo has kept stable across two rewrites, and it moves the
messages away from the rules that produce them.

The locale also rides into the notification email as a header line, so a reply
lands in the language the message was written in.

Everything else is static and needs no server.

## Design notes

### URLs

```
frascella.dev/              en   ← x-default
frascella.dev/privacy/      en
frascella.dev/it/           it
frascella.dev/it/privacy/   it
```

Astro's built-in i18n with `prefixDefaultLocale: false`. Chosen over Italian
at the root because every existing URL keeps working and keeps its authority:
there is nothing to 301, and the CloudPanel package ships an nginx config that
would have had to learn about redirects.

**No automatic redirect by `Accept-Language`.** Google's own guidance is
against it — a crawler presents one language and gets bounced, so the other
version may never be seen — and it takes the choice away from the reader who
deliberately opened the English page. The switcher is the whole mechanism.

### The switcher

Real `<a href>` elements pointing at the *corresponding* page, not at the home
page. `/privacy` → `/it/privacy/`. A switcher that always lands on the home is
a link that loses the reader's place, and it is also a weaker internal-linking
signal than the direct pair.

Each language names itself — "English", "Italiano" — never a flag (that is a
country, not a language) and never a bare two-letter code in the footer (that
is a thing you have to already know). The one you are on is a `<span>` with
`aria-current`, not a link to itself: the same rule `privacy` follows when you
are standing on `/privacy`.

Two placements, and they are not the same control:

- **Footer — a fourth column, `language`**, beside `index` / `elsewhere` /
  `legal`. A heading and a short list of links, exactly like the three next to
  it. It was first built as an `EN · it` pair tucked under `legal` behind a
  hairline, and it read as a widget bolted onto the footer rather than part of
  it. Making it a column is the whole fix. On a phone the four fall into a 2×2.
- **Header — a small `IT ⌄` pill on phones**, left of the menu button, opening
  a paper panel with both languages. On a phone the footer is at the bottom of
  620vh of corridor; this is the shortcut. It renders **only under `html.js`**
  — it needs a script to open, and a button nobody can press is worse than no
  button. Nothing is lost: the footer column is on every page and needs no
  script at all.

The header pill is inside `<header>` and its panel is a sibling **outside** it.
That is not arbitrary: `.nav` carries `mix-blend-mode: difference`, which is
what keeps one white bar legible over both the paper hero and the near-black
corridor, and a blended ancestor inverts anything with a solid background.
Moving the blend down onto `.nav`'s children was tried and fails — `.nav` is
`position: fixed` with a `z-index`, so it is its own stacking context, and a
child blending against an empty backdrop stays exactly as it was: white bars on
white paper, an invisible menu button. The drawer solved this years ago by
living outside the header, and the panel follows it.

### Where the copy lives

`src/data/site.ts` is the single source both the markup and the canvas read,
and that property has to survive. It splits in two rather than growing a
language dimension in place:

```
src/data/site.ts     identity that is not translatable — name, VAT, coords,
                     github, linkedin, email, timezone
src/i18n/en.ts       every translatable string, one tree
src/i18n/it.ts       the same tree, same keys
src/i18n/index.ts    Locale, locales, defaultLocale, getContent(locale),
                     pathFor(locale, path), alternatesFor(path)
```

`it.ts` is typed as `Content`, so a key added to English and forgotten in
Italian is a build error rather than a blank on the page.

Components read `Astro.currentLocale` and call `getContent()`. **No prop
drilling** — `Astro.currentLocale` is derived from the URL and available in
every `.astro` file, so a component does not need to be told where it is.

Client modules read `document.documentElement.lang`, except for the corridor:
`Work.astro` already serialises `data-slab-art` onto the section, and will
serialise the projects the same way. `lib/main.ts` and `lib/scroll.ts` stop
importing `site.ts` altogether and read the DOM. Two wins beyond correctness —
no copy in the JS bundle, and one less place the canvas can drift from the
markup.

### Pages

`src/pages/it/index.astro` and `it/privacy.astro` are three lines each: they
render the same layout the English pages do. Nothing is duplicated — not the
JSON-LD, not the `<style is:global>`, not the composition. The 517-line
`privacy.astro` becomes a renderer over `content.privacy`, which it should
arguably have been already.

### The head, per locale

- `<html lang>` — `en` / `it`.
- `<link rel="canonical">` self-referential per locale.
- `<link rel="alternate" hreflang="en|it|x-default">`, on **both** pages of a
  pair and pointing at each other. Reciprocity is the part Google checks; a
  one-way `hreflang` is discarded silently.
- `og:locale` `en_US` / `it_IT`, plus `og:locale:alternate`.
- Sitemap: `@astrojs/sitemap`'s `i18n` option emits the `xhtml:link` alternates.
  The `/admin` filter stays.
- JSON-LD: `inLanguage` on the `WebSite` and the `WebPage`. The `Person` keeps
  **one** `@id` across both locales — it is one person, not two — while the
  `WebPage` `@id` is per URL. The project descriptions are translated; the
  `CreativeWork` `@id`s stay keyed on the untranslated project name, so both
  graphs describe the same two things.
- The OG card needs no Italian twin: it carries the name, the domain, the
  coordinates and the word "portfolio", which is the same word in Italian.

### Consent

The cookie is per-domain, so switching language does not re-ask. `CONSENT_VERSION`
is **not** bumped: nothing about what is collected changes, and the rule in
CLAUDE.md is explicit that a bump is for a change of scope, not of wording — a
translation is the most literal possible case of "not a change of scope".
Publishing the notice in a second language is a transparency duty, so it gets a
`revisions` entry with `reasked: false`, on both language versions.

### Risk: Italian runs long

Italian is roughly 15–25% longer than English for the same sentence. Three
places are tight and get checked at 390px and at desktop before this ships:

- the hero `h1`, which is already `clamp()`ed to the viewport;
- the accordion row titles, which are two words on one line by design;
- the nav labels, which sit inline at ≥901px with `mix-blend-mode: difference`.

The corridor caption is safe by construction — the blocks are bottom-anchored,
so a longer description grows upward.

## Acceptance criteria

- [x] `/it/` and `/it/privacy/` render fully in Italian: markup, canvas labels,
      form statuses, `alt` text, `aria-label`s, title and description.
      *Checked by rendering both and scanning `innerText` plus every `alt` /
      `aria-label` / `title` / `placeholder` against a list of English-only
      strings. Clean.*
- [x] `it.ts` type-checks against `Content` — no missing or extra keys.
- [x] `hreflang` is reciprocal on all four pages and includes `x-default`;
      `/admin` has none. *3 head links per page, 0 on `/admin`.*
- [x] Sitemap lists 4 URLs with alternates, still excludes `/admin`.
- [x] The switcher goes `/privacy` ↔ `/it/privacy/`, not to the home page, and
      works with JS off. *The footer column does. The header pill is JS-only by
      design and hides itself without it.*
- [x] `POST /api/contact` with `locale: "it"` returns Italian 422 messages;
      without it, English. Exercised with curl: field errors, honeypot, an
      unknown locale, a non-string locale, a successful send, and the cooldown
      in both languages.
- [x] Consent survives a language switch — no second banner.
- [x] `npm run build` and `npm run typecheck` clean; `php -l` on touched files.
- [x] Checked with a headless browser reading `document.body.innerText` on
      `/it/`, not by grepping `dist/` — the rule that caught the work section.
- [x] Screenshots at 390px and desktop for both locales. No horizontal
      overflow at either width in either language.

## What the checks turned up

- **The accordion runs two lines on a phone in Italian** — rows 02–05, against
  only row 05 in English. The outline and fill copies wrap together so the ink
  wipe still lands, and nothing clips or overlaps; the rows are simply taller.
  Left as is: shortening those four headlines to fit a width would be letting
  the layout write the copy.
- **The corridor behaves identically in both languages** — the caption and the
  counter are driven from `data-work-projects`, and a scroll sweep gives the
  same sequence of states on `/` and `/it/`.

## Open questions
